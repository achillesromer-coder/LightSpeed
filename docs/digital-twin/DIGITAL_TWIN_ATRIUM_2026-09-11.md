# ACHILLES Digital Twin Atrium — 2026-09-11

Status: **review / prepublish / evidence-gated**

## Purpose

Provide one coherent interaction and representation layer for the current Römer / ACHILLES digital-twin portfolio. The surface must expose what each twin is, how it is best operated through chat, how it should be visualised, what physical object/system it maps to, what telemetry/evidence it consumes, and which claim gates remain active.

## Governing doctrine

Digital twins are execution and operations infrastructure, not planning-only artefacts:

**design → simulate → test → qualify → integrate → fabricate/commission → living operations**

Digital/analytical closure must never silently promote to physical validation, certification, approval, site selection, safety, deployment or measured performance.

## Standard interaction contract

Every twin surface must expose five panels:

1. **Chat controls** — concrete, bounded questions/actions appropriate to the twin.
2. **Visual representation** — CAD, cutaway, field/thermal map, graph, site plan, object graph or environmental overlay as applicable.
3. **Physical twin** — explicit real-world counterpart and interface boundary.
4. **Telemetry / evidence** — measurements, sensor/config IDs, raw receipts, provenance and uncertainty needed to update state.
5. **Claim gate** — what the digital state does *not* prove.
